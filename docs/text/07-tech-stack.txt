  System architecture
  All channels go through one API, and all slow work runs as queued jobs, so each worker
  type can be scaled on its own.

  The API never calls an AI model directly; it only creates jobs, which keeps owner-facing
  responses fast and lets failed model calls retry without the owner noticing.

  Key flow: one bill, upload to summary
  The bill flow is asynchronous: the owner gets an instant "received", and every later step is
  a queued job that can retry safely.

   1. Receive. Web upload or WhatsApp webhook (signature checked). Compress, compute
       SHA-256; if the hash exists, reply "already received" and stop.
   2. Store. Save the file to object storage; create a documents row with status received ;
       enqueue extract .

   3. Extract. Worker sends the image to the document model with the field schema;
       validate the JSON with Zod; save to extractions ; status extracted . On failure, retry
       up to 3 times, then status needs_manual and ask the owner to type the 3 key values.
   4. Validate. Run rules from doc 03 (PF range, kWh ≤ kVAh, no overlapping period,
       consumer number matches). Mark failing fields low-confidence.
   5. Confirm. Send the confirm screen (web) or one-tap buttons (WhatsApp). On confirm,
      write energy_months with quality tag measured ; status confirmed .
   6. Calculate. Enqueue calculate for the site and month: results row, intensity, baseline
       refit if a new month completes 9+, savings ledger update.
   7. Insights. Run bill health checks; refresh the action plan ranking; update the Green
      Progress Score.
   8. Notify. Enqueue the monthly WhatsApp summary (respecting caps) and any alerts.

  Every job is idempotent: keyed by document ID or site-month, so a retry never double-
  counts.


  Security and privacy
  Security follows the DPDP obligations described in the research report: consent, deletion
  on withdrawal, and breach reporting within 72 hours.


     Area                          Design

     Tenancy                       Row-level security on every table by org_id; API
                                   checks role on every request

     Data in transit and at rest   TLS everywhere; database and storage encrypted
                                   at rest

     Files                         Private buckets; access only through signed URLs
                                   that expire in minutes

     Shares                        Separate share tokens with expiry and named
                                   recipient; every view logged

     Webhooks                      Verify WhatsApp signatures; reject replays

     Secrets                       Stored in the host's secret manager, never in code;
                                   rotated quarterly

  Scalability plan
  The load is light and bursty: bills arrive on DISCOM cycle dates, so the design scales by
  adding queue workers, not by redesigning.

  Capacity at 1 lakh units (3 documents per unit per month):

       Documents: 3,00,000 a month, about 10,000 a day on average; assume 5× on billing
       peaks, about 50,000 a day, under 1 per second. A few workers handle this.
       Document-reading cost: 3,00,000 × ₹0.16 ≈ ₹48,000 a month on paid model rates.
       Storage: 3,00,000 × 300 KB ≈ 90 GB of new files a month; move files older than 18
       months to cold storage.
       Database: about 1 lakh new monthly rows per table; well within one Postgres instance
       for years.
